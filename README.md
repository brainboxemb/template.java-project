# template.java-project

Canonical minimal external reference consumer for [`brainboxemb/tool.java-project`](https://github.com/brainboxemb/tool.java-project).

This repository is intentionally small. Its job is to prove that released Java and repository-orchestration tooling works from a clean, separate repository. It is not a product framework and should not accumulate domain-specific application behaviour.

## Reference-consumer role

The Java project family uses three evidence levels:

```text
tool.git-project + tool.java-project
  owner tests for orchestration and Java domain tooling

          ↓ released tooling contracts

template.java-project
  minimal external conformance/reference consumer

          ↓ proven external contract

real Java repositories
  product-specific implementation and realistic integration evidence
```

Current tooling baseline:

```text
tool.git-project release    v0.2.2
exact Git/Moon commit       d6d760845967f70bd266b3ac2b36c9d5b0edc862
Moon                        2.5.4

tool.java-project release   v0.2.0
exact Java tool commit      9c147850adb9c0c270d852166feae5f08f56c2d6
Java                        Eclipse Temurin 8.0.504+1
Maven                       3.9.16
Maven Wrapper               3.3.4
```

`project.yml` uses the semantic Java tooling ref `v0.2.0`. Committed gitlinks and reusable workflow callers use exact commits behind the released baselines. This combines readable release intent with immutable execution provenance.

## What this repository proves

A normal PR/main build proves:

- clean bootstrap of the released Git and Java tooling on Linux and Windows;
- one high-level `java.canonical` task orchestrated by Moon;
- Moon input hashing and portable output hydration around the stable Java domain action;
- exactly one canonical Linux Maven `verify` when that high-level task needs execution;
- independent native-Windows Maven compatibility verification;
- Windows execution of the exact JAR produced or hydrated by the Linux canonical task;
- readable Surefire evidence generated by the Java domain action;
- one canonical retained Java producer log plus the common `execution.json` envelope;
- a generated evidence map separating producer, domain, orchestration/materialization and publication evidence;
- generated build publication to `dev/pr-N/bld` and `prod/bld`;
- generic cleanup of `dev/pr-N/bld` when the PR closes.

Moon decides whether the high-level Java task needs to execute or can be hydrated. `tool.java-project` remains authoritative for how the canonical Maven lifecycle runs.

## Local use

A normal clone does not require `--recurse-submodules`.

Linux/POSIX:

```bash
git clone https://github.com/brainboxemb/template.java-project.git
cd template.java-project
./bootstrap.sh
tools/tool.git-project/moon-project.sh run consumer:java.canonical --repo .
java -jar bld/artifacts/template-java-project-0.1.0-SNAPSHOT.jar
```

Windows bootstrap remains available through:

```powershell
.\bootstrap.ps1
```

Expected application output:

```text
template.java-project OK
```

Use `update-repo.sh` / `update-repo.ps1` only when deliberately moving a declared tooling release forward.

## Generated evidence

Verified canonical output is published as:

```text
pull request #N  -> dev/pr-N/bld
main             -> prod/bld
```

The generated tree contains the selected JAR, Java producer provenance, raw/readable Surefire evidence and the canonical producer pair:

```text
evidence/executions/java-canonical/
  execution.json
  execution.log
```

The removed legacy alias `evidence/execution.log` is intentionally not retained. The generated top-level `README.md` is the human-facing evidence map and explains the distinction between producer evidence, richer Java/domain evidence, current Moon orchestration/materialization evidence and publication context.

Current Moon evidence is added separately under:

```text
orchestration/
  moon.log
  materialization.json
```

`source-sha.txt` and `evidence/executions/java-canonical/execution.json` belong to the Java producer output. On a valid Moon cache hit they may therefore identify an earlier input-equivalent producer revision. `orchestration/materialization.json` identifies the current revision that requested or hydrated that output. Publication must not rewrite producer evidence to pretend Maven ran again.

## Scope rule

Keep this repository deliberately boring. Add a test here only when it proves a generic Java project-tooling contract that should work for every suitable consumer. Product-specific architecture, services, dependencies and integration scenarios belong in real product repositories instead.
